# 踩坑 05：状态树不一致

> 六段式：现象 → 排查 → 根因 → 5 方案 → Tradeoff 表 → 面试话术

---

## 现象

节点 A 和节点 B 从创世块同步到同一高度，各自计算出来的 `state_root`
却不同。节点 A 认为账户 X 余额 100，节点 B 认为是 90。两个节点互相
不认可对方的区块，链分叉。更诡异的是：重启节点 B 后，状态根又和 A
一致了——说明是运行时状态漂移，不是数据损坏。

## 排查

对比 A、B 两个节点在高度 N 的状态树 dump：
- A 的 storage：`{0x01: 100, 0x02: 50}`
- B 的 storage：`{0x01: 100, 0x02: 50, 0x03: 0}`

多出来一个 `0x03: 0`。这个 key 是某次 SSTORE 写入 0 后没被删除。
MPT 的约定是：**value 为 0 的 key 应该从树中删除**（因为 0 等价于不存在），
但 B 的实现只更新了 value 没删节点，导致树结构多出一个叶子节点，root hash
自然不同。

另一个常见 case：extension 节点合并逻辑错了。两个相邻叶子节点共享前缀
`ab`，应该合并成一个 extension `ab` + branch；B 的代码没合并，导致
树的结构不同（虽然 key/value 完全一样），但 root hash 不同。

## 根因

MPT 的 root hash 不仅依赖 key/value 内容，还依赖**树的结构**。同样的
key/value 集合，插 entry 的顺序不同、删除时合并逻辑不同、空 value 处理
不同，都会产生不同的树结构，进而不同的 root hash。

区块链要求所有节点对"同一状态"算出同一个 root hash，否则共识失败。
这意味着 MPT 实现必须是**确定性**的：相同输入永远产生相同树结构。
任何"看起来 key/value 对就行"的宽松实现，都会导致状态根不一致。

## 5 个方案

| # | 方案 | 原理 | 优点 | 缺点 |
|---|------|------|------|------|
| 1 | 严格实现 MPT | 完全按黄皮书实现 leaf/ext/branch | 与以太坊对齐 | 实现复杂、易出 bug |
| 2 | 用 OrderedDict | 改 key 时按字典序重排 | 简单 | 仍然要处理空 value |
| 3 | 空 value 删除 | SSTORE 0 时删除节点 | 符合约定 | 边界 case 多 |
| 4 | 树规范化 | 每次 update 后合并相邻 extension | 结构统一 | 额外开销 |
| 5 | 用成熟库 | 直接引入 py-trie / merkle-trie | 零 bug | 依赖外部库 |

### Tradeoff 表

| 方案 | 实现复杂度 | 与以太坊兼容 | 性能 | 适合场景 |
|------|-----------|--------------|------|---------|
| 手写严格 MPT | 极高 | 完全兼容 | 中 | 学习/研究 |
| OrderedDict + 排序 | 低 | 不兼容（root 对不上） | 高 | 内部工具 |
| 用成熟库 | 低 | 完全兼容 | 高 | 生产项目 |
| 树规范化 | 中 | 完全兼容 | 低（重排开销） | 学术研究 |

## 面试话术

"状态根不一致是 MPT 实现的经典坑。我们踩过的是 SSTORE 写 0 后没删节点，
树里多了个 value=0 的叶子，root hash 就和别人对不上了。修复方案是：
SSTORE 时如果新 value 是 0，直接从树里删掉这个 key。另一个坑是 extension
节点合并：两个叶子共享前缀时必须合并成 extension，否则树结构和以太坊
不一样，root 也对不上。这个问题的本质是：**MPT 的 root hash 不仅依赖
key/value，还依赖树结构**，所以实现必须严格按黄皮书来，不能'差不多就行'。
我们最后选择直接用成熟库 py-trie，因为手写一个 MPT 看着只有几百行代码，
但边界 case（空路径、单点分支、删除后合并）能调一周。生产项目的原则是：
密码学相关组件，能复用就不要自己写。"
